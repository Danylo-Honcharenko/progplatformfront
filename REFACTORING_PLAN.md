# План рефакторинга ProgPlatform: переход на Feature-Sliced Design

## 1. Цель и границы

Сделать фронтенд понятным по пользовательским сценариям: вход, личный кабинет, изучение курса, прохождение теста. У каждой части должны быть ясная ответственность, предсказуемое состояние и проверяемое поведение.

Рекомендуется постепенная переработка в текущем приложении: исправить критические ошибки, настроить инструменты, затем переносить законченные сценарии. Полная замена проекта за один заход усложнит проверку поведения и совместимости с API.

План основан на чтении исходников и запуске `npm run build` 10 сентября 2026 года. Сборка завершилась двумя ошибками TypeScript. Приложение в браузере и backend не проверялись; замечания об интерфейсе основаны на разметке. Ниже описаны предлагаемые изменения, а не уже выполненный рефакторинг.

## 3. Архитектура без лишнего дробления

Использовать направление зависимостей `app → pages → features → entities → shared`. Внешние импорты слайса идут через его публичный API; соседние слайсы одного слоя не импортируют друг друга. Внутри слайса допустимы относительные импорты. `app` и `shared` организуются по техническим сегментам, без бизнес-слайсов. Основание: [слои FSD](https://fsd.how/docs/reference/layers/) и [публичный API](https://fsd.how/docs/reference/public-api/).

Для этого небольшого проекта пока достаточно пяти слоёв. `widgets` не нужен: общий каркас находится в `app`, уникальные блоки — внутри страниц. Не создавать `entities/topic`, `entities/module` и `entities/exercise` только потому, что backend возвращает такие объекты. На первом этапе они составляют модель курса.

Предлагаемая структура:

```text
src/
  main.tsx
  app/
    entrypoint/             # App и подключение приложения
    providers/              # QueryClient и другие необходимые провайдеры
    routes/                 # Router, RequireSession, обработка 404
    layouts/                # PublicLayout, AccountLayout, меню аккаунта
    styles/                 # Глобальные стили и дизайн-токены
  pages/
    home/                   # ui/, локальные assets/
    login/                  # ui/, model/, api/
    registration/           # ui/, model/, api/
    dashboard/              # ui/ и композиция запросов
    profile/                # ui/
    course/                 # ui/, model/, api/: обучение и тестирование
    change-password/        # Добавить рабочий сценарий после согласования API
    not-found/              # ui/
  features/
    sign-out/               # api/, model/, ui/: выход из аккаунта
  entities/
    user/                   # api/, model/, ui/: пользователь и сессия
    course/                 # api/, model/, ui/: курс, модули, темы, тесты
    test-result/            # api/, model/, ui/: результат и история попыток
  shared/
    api/                    # HTTP-клиент, ApiEnvelope, ApiError
    config/                 # Публичная конфигурация окружения
    routes/                 # Пути и функции построения URL
    ui/                     # Примитивы, Container, Markdown, состояния
    lib/                    # Узкие библиотеки, например class-names
```

Создавать сегменты только при наличии содержимого. У слайса — небольшой `index.ts` с явными экспортами. Не создавать общий `entities/index.ts` или один экспорт всего приложения. Внутри слайса не импортировать собственный `index.ts`, чтобы не провоцировать циклы.

Пример внешнего импорта: `import { courseQueries } from '@/entities/course'`. Для UI допустим отдельный вход `@/shared/ui/button`. Уникальные формы входа и регистрации могут оставаться в своих страницах. Выделять их в `features` следует при реальном повторном использовании. Это проектное решение, а не требование «сделать фичей каждую кнопку».

## 5. Данные, API и сессия

### Серверные данные

Рекомендую добавить [TanStack Query](https://tanstack.com/query/latest/docs/framework/react/overview) для загрузки, кеширования и обновления серверных данных. Сейчас эти обязанности вручную повторяются в `useEffect`. Не дублировать полученный курс и пользователя в отдельном глобальном store.

- `entities/user` владеет запросом текущего пользователя; Header и страницы используют общий кеш.
- Ключ курса включает ID курса и текущего пользователя: `['course', userId, courseId]`.
- Запрос защищённых данных включается после успешного определения сессии.
- После завершения темы обновляются данные курса и список курсов; после теста — также история результатов и баллы пользователя.
- При выходе отменяются активные приватные запросы и очищаются пользовательские данные кеша. Проверить переход между двумя аккаунтами.
- Не повторять автоматически 401/403 и отправку теста: повторная мутация может создать лишнюю попытку.

Конкретные сроки актуальности кеша определить по поведению продукта. Сам факт установки библиотеки не решает вопрос синхронизации.

### Контракты и ошибки

- Типизировать результат каждого запроса. Переименовать общий `Response<T>` в `ApiEnvelope<T>`, чтобы не путать его с HTTP Response.
- В API-функциях извлекать транспортную оболочку; компонентам отдавать полезные данные. Уточнить, всегда ли `status` в теле совпадает с HTTP-статусом.
- Превращать пойманное `unknown` в `ApiError`: `kind`, необязательный `status`, `message`, ошибки полей и идентификатор обращения. Не предполагать, что `response` существует.
- Передавать query-параметры через Axios `params`; проверять `courseId` до запроса. Не отправлять `undefined` в обязательных параметрах.
- `AnswerResponse` разделить по назначению: данные отправки ответа и данные проверки. `FieldErrorResponse` сделать типом, а не классом без поведения.
- Вложенные DTO курса оставить локальными для `entities/course`. `entities/test-result` не должен импортировать внутренности соседней сущности; согласование результатов и вопросов выполняет страница курса.
- Удалить `responseUserDataHandler`: проверка на `undefined` с callback не добавляет полезной абстракции.

### Авторизация и окружение

`RequireSession` в `app/routes` различает загрузку сессии, гостя и ошибку сервера. На страницу входа отправлять при отсутствии сессии, а не при любой сетевой ошибке. После входа возвращать пользователя на исходный разрешённый внутренний маршрут.

Вынести адрес API в `VITE_API_URL`, добавить `.env.example`. Эти переменные попадают в клиентский bundle и не предназначены для секретов. Политику `withCredentials` согласовать с cookie/CORS backend и применять последовательно. Нынешнюю cookie-схему не заменять хранением токена в localStorage без отдельной причины.

Сервер должен самостоятельно проверять право доступа к курсу и принадлежность прогресса. Передаваемый сейчас `userId` не является доказательством авторизации; удалять его из запросов можно только после изменения серверного контракта.

## 6. Как переписать учебный сценарий

`CoursePage.tsx` сейчас объединяет загрузку, выбор модуля, чтение темы, завершение темы, форму теста и результат. Разделить внутри `pages/course`:

- `CoursePage` — параметры маршрута, загрузка и выбор представления.
- `ModuleList` — список модулей и прогресс.
- `TopicReader` — содержимое темы, навигация и действие завершения.
- `QuizForm` — вопросы, выбранные ответы и отправка.
- `QuizResult` — баллы и обратная связь.
- `model/` — выбор текущего состояния и подготовка данных; `api/` — мутации.

Вместо `open`, `openTest` и копий `topics`/`topic` хранить выбранные ID и явное состояние экрана. Объекты получать из актуального курса. Лучше сохранять выбор в URL, например `/course/12?module=3&topic=7&view=quiz`: refresh и кнопка Back должны восстанавливать положение. Невалидные ID и режим без теста возвращают понятное состояние, а не исключение.

Ответы хранить по устойчивому ID вопроса. Сейчас API передаёт текст вопроса без ID: для надёжного решения потребуется изменение backend. До него использовать локальный ключ в пределах попытки, а преобразование в нынешний текстовый payload выполнять перед отправкой. Ограничение с одинаковыми текстами вопросов явно зафиксировать.

При смене теста сбрасывать ответы и результат, во время отправки блокировать повторный submit. Проверять наличие теста перед обращением к `tests[0]`; если тестов может быть несколько, добавить выбор, а не молча показывать первый. Нумерацию тем получать через `map`, отдельный `Map` здесь не нужен.

## 7. Формы и интерфейс

Сначала достаточно типизированного состояния простых форм и общих полей; отдельная библиотека форм не обязательна. Обработчики submit должны соответствовать событию отправки формы, а не `ChangeEvent`. При росте валидации выбрать один общий инструмент, не несколько параллельных подходов.

- Общие `FormField`, `FormError`, `SubmitButton`; доменные правила остаются у формы.
- Видимые `label`, `type="email"`, корректные `autoComplete`, связь ошибки с полем через `aria-describedby`.
- Отдельные состояния загрузки, отсутствия данных и ошибки с повтором запроса.
- Закрываемые диалоги ошибок; обычные ошибки запроса лучше показывать рядом с содержимым.
- Один адаптивный `Container` вместо `pl-44`, `pl-35`, фиксированных карточек и `w-1/2` для основного контента.
- Для длинных экранов — минимальная высота и естественная прокрутка; проверить мобильную клавиатуру, длинный Markdown и блоки кода.
- Сохранить Radix/shadcn-примитивы, унифицировать отступы, типографику, радиусы и цвета через токены.
- Связать radio с подписями через `id`/`htmlFor`; дать кнопке завершения темы доступное имя; не передавать правильность ответа только цветом.
- В `Home.tsx` исправить повторяющийся текст, иерархию заголовков и использование `nav` для обычного описательного списка. Определить единое название: сейчас встречаются ProgPlatform и PyLearn.

Красивый результат проверить в браузере на узком, среднем и широком экране, с клавиатуры и при длинном содержимом. Архитектурный перенос сам по себе не подтверждает качество интерфейса.

## 8. Что убрать или отложить

**Удалить при переносе:** отладочные `console.log`, закомментированную ветку администратора, пустые эффекты и дублированное состояние, `responseUserDataHandler`, прежние папки после переноса всех потребителей.

**Очистить после проверки использования:** старые административные и popup-правила в `App.scss` — поиск обнаруживает перечисленные классы только в самом SCSS. Сохранить или заменить используемый `.form-container`. Если SCSS больше не нужен, удалить Sass и обновить lockfile.

**Не удалять вслепую:** Radix-компоненты и зависимости. Например, `next-themes` используется внутри `ui/sonner.tsx`, но сам Toaster не подключён к приложению. Сначала решить, нужны ли уведомления и темы, затем убрать неиспользуемую цепочку целиком.

**Убрать из доступного UI до реализации:** кнопку задания с единственным `console.log`, неработающую смену пароля. Блок Windows-приложения с отключённым скачиванием оставить только при актуальном продуктовом намерении. Это изменение доступных возможностей, его следует явно отметить в PR.

**Заменить:** favicon Vite, на который ещё ссылается `index.html`; после замены удалить `public/vite.svg`. Изображения главной держать рядом с `pages/home`, исправить опечатки имён вместе с импортами.

Не вводить Redux/Zustand, универсальный repository layer, отдельный пакет UI или абстрактный CRUD-конструктор без конкретной потребности.

## 9. Инструменты и проверки

Сейчас есть только `dev`, `build`, `preview`; тестов нет. `eslint.config.js` ссылается на незаявленные зависимости. Сначала восстановить согласованный набор ESLint, TypeScript ESLint и React Hooks/Refresh plugins. Добавить форматтер с единым стилем, например 2 пробела, одинарные кавычки и точки с запятой; форматировать переносимые файлы отдельными понятными изменениями.

Предлагаемые команды после настройки:

| Команда | Назначение |
| --- | --- |
| `npm run lint` | ESLint, хуки и ограничения импортов между слоями |
| `npm run format:check` | Проверка форматирования |
| `npm run typecheck` | TypeScript без production bundle |
| `npm run test` | Локальный запуск тестов |
| `npm run test:ci` | Однократный прогон в CI |
| `npm run build` | Типы и production-сборка |

Для модульных и компонентных тестов подходит [Vitest](https://vitest.dev/guide/). При установке проверить совместимость выбранной версии с текущими Node и Vite; не совмещать архитектурный перенос с бесконтрольным обновлением всех зависимостей. Тесты размещать рядом с кодом: `*.test.ts` и `*.test.tsx`.

Приоритет — регрессии реальных сценариев:

1. Ответы сохраняются при повторном рендере, смена теста сбрасывает попытку, двойная отправка блокируется.
2. 401 приводит ко входу; timeout/500 показывают повтор запроса; загрузка завершается при ошибке.
3. Смена курса в URL загружает новый курс; несуществующие модуль/тема и пустые тесты безопасны.
4. Завершение темы обновляет прогресс без мутации предыдущего состояния.
5. Выход и вход другим пользователем не показывают прежние приватные данные.
6. Ошибки формы видны у полей; повторная отправка работает.

Проверять наблюдаемое поведение, а не количество вызовов сеттера или внутреннюю структуру компонентов. Процент покрытия пока не назначать; обязательными сделать эти сценарии. В CI запускать установку по lockfile, lint, форматирование, тесты и build.

- [ ] **Этап 6 — визуальная унификация.** Переработать главную, формы и адаптивность, проверить клавиатуру и длинный контент. Результат: согласованный интерфейс без неработающих действий.
- [ ] **Этап 7 — очистка.** Удалить старые файлы и неиспользуемые зависимости, обновить README и AGENTS.md, включить проверки в CI. Результат: нет импортов из прежней структуры.

Каждый этап оформлять небольшими PR с описанием изменённого поведения и проверками. Во время миграции старый код может использовать новые публичные API; новые слои не должны зависеть от старых страниц и глобальных сервисов.

## 11. Что уточнить по backend перед реализацией

- Контракт смены пароля и необходимость email при действующей сессии.
- Источник пользовательской идентичности, cookie/CORS и CSRF-защита мутаций.
- Устойчивые ID вопросов/ответов, число тестов у темы, правила повторной попытки.
- Может ли завершение темы повторяться безопасно; какие данные возвращает мутация.
- Формат ошибок, nullable-поля, допустимые роли и поведение входа для роли, отличной от `ROLE_USER`.
- Границы уровней: текущий текст профиля не объясняет случаи ровно 10 и 20 баллов; правила должен задавать backend.

Эти вопросы не мешают начать этапы 1–2. Изменение endpoint, payload или правил начисления баллов требует согласования серверного контракта.
